# Generating and Combining Compilation Databases

## Start From the Actual Build

Inventory the workspace before choosing a generator:

```bash
realpath .
find . -name compile_commands.json -type f -print
find . -name CMakeCache.txt -o -name build.ninja -o -name '.*.cmd'
rg -n 'CMAKE_EXPORT_COMPILE_COMMANDS|gen_compile_commands|compdb' .
```

Identify which components were really compiled, their source roots, their build
directories, and whether compilation occurred on the host or in a container.
Do not equate “repository exists” with “repository was built.”

## Prefer Native Metadata

Use the most authoritative available source:

| Build system | Preferred source |
| --- | --- |
| CMake | Configure with `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`; use the database in the build directory |
| Meson | Use `<build-dir>/compile_commands.json` generated by Meson/Ninja |
| Ninja | Prefer the generator database; otherwise use `ninja -C <build-dir> -t compdb` with the relevant rules |
| Linux/U-Boot/Kbuild | Use the tree's `scripts/clang-tools/gen_compile_commands.py` and existing `.cmd` files |
| Make/Autotools without metadata | Capture a real incremental build with Bear or `intercept-build` when available |
| Custom firmware Makefiles | Prefer stored command files; otherwise use a forced dry run only after proving it expands the same configuration |

Never parse human progress lines such as `CC foo.o` when the full compiler
invocation is available elsewhere.

### CMake

For a new or safely reconfigurable build directory:

```bash
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build
```

The database belongs to `build/`. Either point clangd there, create a project
root symlink when appropriate, or merge it into the workspace database.

### Meson and Ninja

Meson normally writes the database during setup:

```bash
meson setup build
meson compile -C build
```

For a Ninja project lacking a database, inspect rule names first:

```bash
ninja -C build -t rules
ninja -C build -t compdb <c-rule> <cxx-rule> > compile_commands.json
```

Do not guess rule names or treat link commands as compile commands.

### Make Capture

When no persistent metadata exists, command interception must observe actual
compiler executions. A no-op incremental build yields an empty capture, while a
clean rebuild may be expensive or destructive. Explain this tradeoff before
forcing a rebuild.

## Database Semantics

Each entry requires:

- `directory`: working directory used by the compiler;
- `file`: translation unit, absolute or relative to `directory`;
- exactly one of `command` or `arguments`;
- optional `output`.

Relative `-I`, forced includes, generated headers, response files, and output
paths are interpreted from `directory`. Changing only `file` is therefore not a
complete path repair.

Multiple entries for one file are valid. Keep them when they differ by target,
configuration, image stage, or important defines.

## Container and Remote Builds

A database generated in a container may contain valid but host-inaccessible
paths in all string fields, including compiler names and `-I`/`--sysroot`
arguments. Establish explicit mappings such as:

```text
/work/project -> /home/user/project
```

Then rewrite the complete JSON structure:

```bash
python3 scripts/compile_db.py rewrite \
  compile_commands.json \
  --map /work/project=/home/user/project \
  --output compile_commands.host.json
```

Path rewriting does not provide container-only system headers. Choose one of:

- run clangd in the same development container with compatible workspace URIs;
- install the matching development headers on the host when authorized;
- stage only the referenced headers/sysroot into a project cache and rewrite
  those include prefixes;
- use an existing project toolchain/sysroot.

Validate exact compiler and header versions rather than silently mixing host and
container environments.

## Combining Components

For a workspace containing firmware, kernel, host tools, or generated packages:

1. generate each component database with its own native mechanism;
2. map container/old prefixes to the one real workspace path;
3. canonicalize `directory` and `file` while retaining command semantics;
4. merge and deduplicate exact invocations;
5. sort for deterministic output;
6. inspect counts by source prefix and test one file per component.

Use the bundled tool:

```bash
python3 scripts/compile_db.py merge \
  --output compile_commands.json \
  --canonicalize \
  component-a/compile_commands.json component-b/build/compile_commands.json

python3 scripts/compile_db.py inspect compile_commands.json \
  --workspace "$(realpath .)"
```

If a component lacks recoverable command metadata, report it as uncovered. Do
not synthesize a plausible-looking command and call the database complete.
